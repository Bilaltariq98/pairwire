Section 01

The Internet's Transport Problem

For 40 years, the internet ran on two transport protocols: TCP (reliable, ordered) and UDP (unreliable, fast). Every real-time application had to pick its poison:

TCP

Reliable & ordered — every byte arrives, in order.

One lost packet blocks everything behind it (head-of-line blocking).

Handshake: 1 RTT (TCP) + 1-2 RTT (TLS) = 2-3 round trips before data flows.

vs
UDP

Fast & unreliable — fire-and-forget packets.

No congestion control, no encryption, no ordering. You build everything yourself.

Used by: WebRTC, game engines, DNS. Each reimplements reliability ad-hoc.

For pair programming, you need both behaviors simultaneously:

Must be reliable

Keyboard events, clipboard data, control handoff — every byte must arrive, in order. A dropped keystroke means garbled input.

Must be fast, loss-tolerant

Cursor position at 60Hz, screen frames at 30fps — old data is worthless. Retransmitting a stale cursor position is worse than dropping it.

TCP gives you reliability but kills latency. UDP gives you speed but no guarantees. What if there was a protocol that gave you both, letting you choose per-stream?

That protocol is QUIC. It's the foundation everything in pairwire is built on. Let's understand it from the ground up.
Section 02

QUIC — The Foundation

QUIC is a transport protocol built on top of UDP. It was designed by Google, standardized as RFC 9000 in 2021, and is now the backbone of HTTP/3. But QUIC isn't just "faster TCP" — it's a fundamentally different design.

What Makes QUIC Different

01
Encryption is mandatory
QUIC integrates TLS 1.3 directly into its handshake. There is no unencrypted QUIC. The handshake completes in 1 RTT (or 0-RTT on reconnection) — compared to TCP's 2-3 RTT for TCP+TLS. Every byte on the wire is authenticated and encrypted.
02
Multiplexed streams, no head-of-line blocking
A single QUIC connection carries many independent streams. If packet 47 on stream A is lost, only stream A pauses for retransmission. Streams B, C, D keep flowing. In TCP, one lost packet blocks everything. This is the killer feature for real-time apps.
03
Connection migration
QUIC connections are identified by a connection ID, not the IP:port tuple. Switch from WiFi to cellular? The QUIC connection survives. TCP would need to re-handshake.
04
Datagrams (RFC 9221)
QUIC added native unreliable datagrams — messages that benefit from QUIC's encryption and congestion control, but are not retransmitted if lost. Perfect for cursor positions, game state, and anything where freshness beats completeness.

QUIC vs TCP vs WebRTC

Property TCP WebRTC QUIC
Handshake 2-3 RTT ICE + DTLS = 4-8 RTT 1 RTT (0-RTT on resume)
Encryption Optional (TLS layer) Mandatory (DTLS) Mandatory (TLS 1.3 built-in)
Multiplexing Single byte stream Data channels (SCTP) Native streams + datagrams
HOL blocking Yes — one loss blocks all Per-channel Per-stream — independent
NAT traversal Needs STUN/TURN ICE built-in Needs a helper (iroh provides this)
Unreliable data No Yes (unordered channels) Yes (datagrams, RFC 9221)
Why not WebRTC? WebRTC was designed for browsers. It mandates SDP offer/answer negotiation, ICE candidate gathering, and SRTP for media — all complexity that a native Rust app doesn't need. QUIC gives us the same capabilities (encryption, multiplexing, unreliable data) with a much simpler API and a single handshake.

Quinn — The Rust QUIC Implementation

Quinn is the reference QUIC implementation in Rust. It provides the low-level QUIC protocol: connection setup, stream management, congestion control, and encryption. It's battle-tested and spec-compliant.

Pairwire doesn't use Quinn directly — it uses iroh, which wraps Quinn (via its own fork called noq) and adds P2P connectivity on top. But Quinn is what's actually moving the bytes.

// Conceptually, this is what Quinn gives you: let conn = endpoint.connect(addr, "pairwire/1").await?; // Open multiple independent streams on one connection let (send, recv) = conn.open_bi().await?; // bidirectional let send = conn.open_uni().await?; // unidirectional conn.send_datagram(bytes)?; // unreliable
Section 03

Three Primitives: Streams & Datagrams

QUIC gives you exactly three transport primitives. Every feature in pairwire maps to one of these three. Understanding them is understanding the whole networking model.

QUIC Transport Primitives

1. Bidirectional Streams — open_bi()

A bidirectional stream is like a TCP connection within your QUIC connection. Data flows in both directions, it's reliable (lost packets are retransmitted), and it's ordered (bytes arrive in the order they were sent).

In pairwire: The control stream is bidirectional. Both peers send ControlMessage on the same stream — handshake, capability negotiation, sharing toggles, goodbye messages. It's the command channel of the session.
// Host opens control stream let (send, recv) = conn.open_bi().await?; // Both sides can send and receive ControlMessages send_message(&send, &ControlMessage::Handshake { ... }).await?; let msg: ControlMessage = recv_message(&recv).await?;

2. Unidirectional Streams — open_uni()

Data flows in one direction only. The sender writes, the receiver reads. Still reliable and ordered, but there's no response channel — if you need to reply, you open a stream in the other direction.

In pairwire: The guest uses a unidirectional stream to send input events (keyboard, mouse, clipboard) to the host. Input is one-way: guest types, host receives. Using a separate stream from control means input events don't get head-of-line blocked by a large clipboard sync on the control stream.

moq-lite also uses unidirectional streams extensively — each group of media data (a keyframe and its dependent frames) ships on its own uni stream. If one group is lost, the next group arrives independently.

3. Datagrams — send_datagram()

Datagrams are the wildcard. They're unreliable (the sender never knows if they arrived), unordered (they may arrive in any sequence), and size-limited (~1200 bytes, the QUIC MTU).

But they benefit from QUIC's encryption and congestion control — unlike raw UDP, datagrams are still authenticated and won't flood the network.

In pairwire: Cursor positions are sent as datagrams at 60Hz. Each CursorUpdate is ~10-15 bytes — peer ID, X/Y coordinates, visibility, click animation state. If a cursor update is lost, the next one arrives 16ms later with the current position. Retransmitting a stale position would actually be worse than dropping it.

Why Three Primitives Matter

The key insight is that different types of data have different delivery requirements. QUIC lets you match the transport to the data:

Data Type Primitive Why
Control messages Bidirectional stream Both peers negotiate; must be reliable
Input events Unidirectional stream One-way guest→host; must be reliable
Cursor positions Datagram Ephemeral, 60Hz; stale data is useless
Screen frames Uni streams (via moq-lite) Each group on its own stream; no HOL blocking
Audio frames Uni streams (via moq-lite) Same as video; priority scheduling ensures audio wins
Section 04

iroh — P2P Without the Pain

QUIC handles the protocol. But how do two peers find each other and connect when they're both behind NATs? That's iroh's job.

The NAT Problem

Most devices sit behind a NAT (Network Address Translation) — your router assigns private IPs (192.168.x.x) and maps them to a single public IP. Two peers behind different NATs can't directly reach each other because neither knows the other's address.

NAT Traversal Problem

iroh's Solution

iroh (by n0, Inc.) is a Rust library that provides P2P connectivity using QUIC. It solves the NAT problem with a multi-strategy approach:

1. Direct Connection

Both peers send their public+private addresses to iroh's relay. If they're on the same LAN, they connect directly via private IP. If both NATs are permissive, UDP hole-punching creates a direct path.

2. Relay Fallback

If direct connection fails (~10% of the time), iroh routes traffic through a relay server. The relay can't read the content (QUIC encryption), it just forwards packets. Adds ~20-50ms latency.

The Endpoint

iroh's central type is Endpoint — a singleton that manages all connections. Each endpoint has a unique EndpointId (an ed25519 public key). Think of it as your identity on the network.

// Create an endpoint — this is pairwire's entry point to the network let endpoint = Endpoint::builder() .alpns(vec![b"pairwire/1".to_vec()]) // protocol identifier .bind().await?; // Your identity on the network let my_id = endpoint.endpoint_id(); // ed25519 public key // Host: accept incoming connections let conn = endpoint.accept().await?; // Guest: connect to host using their EndpointAddr let conn = endpoint.connect(host_addr, b"pairwire/1").await?;
Critical rule: Only one Endpoint per process. Creating multiple would bind multiple UDP sockets and break NAT traversal. iroh's endpoint is the singleton that manages all your connections.

The Invite Link

When a host starts a session, pairwire encodes the connection info into an invite link:

pairwire://0f02581240ab?relay=euc1.relay.pairwire.sh&token=eyJ...
├── 0f02581240ab endpoint ID (ed25519 pubkey, hex)
├── relay=... relay URL for NAT fallback
└── token=... 16-byte session token (auth)

The guest parses this link, constructs an EndpointAddr, and calls endpoint.connect(). iroh handles the rest — it tries direct connection first, falls back to relay if needed, and upgrades to direct later if possible.

Section 05

moq-lite — Media over QUIC

We have a QUIC connection. We can open streams and send datagrams. But how do you stream media — video frames, audio samples — in a way that handles congestion, prioritization, and multi-party fanout? That's moq-lite.

What is MoQ?

Media over QUIC (MoQ) is an IETF draft standard for live media delivery over QUIC. The full spec (moq-transport) is designed for CDN-scale streaming. moq-lite is a streamlined, forward-compatible subset created by the moq-dev team — it strips out the CDN complexity while keeping the core model.

The Core Model

moq-lite organizes media in a hierarchy:

moq-lite Data Hierarchy

Broadcast

A named collection of tracks. Think of it as a "session" — everything one host is publishing. Named like "pairwire/session".

Track

A named media stream within a broadcast. Has a priority (lower = more important). Examples: "screen", "audio/host", "audio/guest_1".

Group

A sequence of frames that can be decoded independently. Each keyframe starts a new group. Each group maps to exactly one QUIC uni stream.

Frame

The smallest unit of media. A single encoded video frame (I-frame or P-frame) or audio packet (20ms Opus). Frames within a group are ordered.

Why Group = QUIC Stream?

This is the key architectural insight of moq-lite. By putting each group on its own QUIC stream:

No head-of-line blocking between groups. If Group 5 has a lost packet, it doesn't block Group 6. The receiver can start decoding Group 6 (which starts with a keyframe) immediately. This is impossible with TCP, where a lost packet in an earlier frame blocks all subsequent frames.

Priority & Congestion

When bandwidth is tight, moq-lite makes smart decisions:

Rule Effect
Higher-priority tracks first Audio (priority 0) always beats video (priority 1). You hear before you see.
Newer groups first Within a track, the latest group ships before older ones. You see the current frame, not a frame from 2 seconds ago.
Old groups are droppable If congestion is severe, old groups that haven't fully sent are abandoned. The receiver skips to the next keyframe.
This is relay-friendly. A moq-lite relay can make these priority decisions without understanding the media content. It just reads the track priority and group sequence numbers. This is what makes multi-party scalable — the relay doesn't decode video.

Publisher & Subscriber

moq-lite uses a pub/sub model:

Publisher (Host)

Creates a broadcast with tracks.

Writes frames to tracks.

moq-lite opens QUIC streams as needed.

→
Subscriber (Guest)

Subscribes to a broadcast.

Receives frames via broadcast channel.

moq-lite reads from QUIC streams.

Section 06

hang — Media Framing

moq-lite handles transport — getting bytes from A to B with priority. hang adds the media semantics: "this frame is 1920x1080 H.264 at timestamp 33ms."

Think of the layers like this:

Protocol Layer Stack

What hang Adds

Catalog Track

A special moq-lite track that describes all other tracks — their codecs, sample rates, dimensions. The subscriber reads the catalog first to know what to expect. WebCodecs-compatible format.

Frame Headers

Each frame gets a timestamp (microsecond precision) and codec payload type. The receiver knows when to display each frame and what decoder to use.

Per-Source Tracks

In multi-party, each participant gets their own tracks: "audio/host", "audio/guest_1", "audio/guest_2". The subscriber can mix them independently.

WebCodecs Alignment

hang frames are designed to be directly consumable by WebCodecs (the browser API). This means a future web viewer can play pairwire streams natively — no transcoding.

Section 07

Pairwire's Transport Layer

Now let's see how pairwire uses all of these building blocks. The transport crate (crates/transport/) is where iroh, moq-lite, and raw QUIC meet.

PairwireConnection

The core wrapper around an iroh QUIC connection. It provides high-level methods that abstract the primitive selection:

pub struct PairwireConnection { conn: iroh::Connection, } impl PairwireConnection { // Control — bidirectional stream, priority 1 pub async fn open_control_stream(&self) -> (SendStream, RecvStream); // Input — unidirectional stream, priority 1 pub async fn open_input_stream(&self) -> SendStream; // Datagrams — unreliable cursor updates pub fn send_datagram(&self, bytes: Bytes) -> Result<()>; pub async fn recv_datagram(&self) -> Result<Bytes>; // Message framing — postcard serialize + length-prefix pub async fn send_message<T: Serialize>(&self, stream: &SendStream, msg: &T); pub async fn recv_message<T: DeserializeOwned>(&self, stream: &RecvStream) -> T; }

The Web Transport Adapter

moq-lite doesn't know about iroh — it speaks the web-transport-trait interface. Pairwire bridges this with IrohWtSession:

// Adapter: iroh connection → web-transport-trait Session pub struct IrohWtSession { conn: Connection, } impl Session for IrohWtSession { async fn accept_uni(&self) -> WtRecvStream { ... } async fn accept_bi(&self) -> (WtSendStream, WtRecvStream) { ... } async fn open_uni(&self) -> WtSendStream { ... } async fn open_bi(&self) -> (WtSendStream, WtRecvStream) { ... } }

This adapter means moq-lite's Server and Client work over iroh connections without modification. If iroh changes its API, only this adapter needs updating.

Section 09

The Media Pipeline

This is the hot path — the journey of a single screen frame from the host's display to the guest's viewer. Every millisecond matters.

End-to-End Frame Journey

Screen Frame Pipeline (Host → Guest)

Key Design Decisions

Why OS threads for capture & encode?

scap's capture callback runs on its own OS thread — you can't control it. FFmpeg encoder/decoder contexts are not Send (they can't be moved between threads). So both must live on dedicated OS threads, not tokio tasks. Channels bridge the thread/async boundary.

Why bounded channels?

Unbounded channels would let the capture thread outpace the encoder during CPU spikes, accumulating stale frames and growing memory. Bounded channels (capacity 4) create natural backpressure — if the encoder is behind, the newest frames overwrite the oldest.

Why keyframe = new moq-lite group?

A guest joining mid-stream can start decoding from the next keyframe without waiting for the full group-of-pictures history. And if a group is partially lost to congestion, the receiver just skips to the next group/keyframe rather than displaying corruption.

Audio Pipeline

Audio follows a similar pattern but simpler — Opus frames are small (20ms = ~80 bytes at 32kbps) and always independently decodable:

Host: cpal capture → Opus encode → moq-lite audio track → QUIC Guest: QUIC → moq-lite subscribe → Opus decode → ring buffer → cpal playback Jitter buffer: 2 frames = 40ms of buffering Bandwidth: ~32 Kbps per direction (negligible) Priority: 0 (highest — audio always ships before video)
Section 10

Quality Adaptation

Network conditions change. WiFi congestion, relay hops, cellular handoffs. Pairwire monitors the connection in real-time and adapts encoding parameters without restarting the encoder.

The Quality Monitor

The QualityMonitor polls QUIC connection stats every 1 second and emits a ConnectionHealth snapshot:

pub struct ConnectionHealth { pub rtt_ms: u32, // Round-trip time in milliseconds pub loss_per_mille: u16, // Packet loss × 1000 (5000 = 5%) }

Adaptation Tiers

Condition Tier Resolution FPS Keyframe
Loss ≤ 5%, RTT ≤ 200ms Full 1080p 30 2s
Loss 5-15% or RTT > 200ms Reduced 720p 15 5s
Loss > 15% Degraded 720p 15 4s
Hysteresis: The monitor requires 3 consecutive "Full" samples before upgrading from Reduced/Degraded back to Full. This prevents the encoder from oscillating between quality levels during transient congestion.

The new CaptureConfig is delivered to the encode thread via a tokio::sync::watch channel. The encoder checks for config changes between frames and reconfigures without restarting — resolution changes just update the scaler, FPS changes adjust the frame skip counter.

Section 11

The Protocol Messages

Everything on the wire is a message defined in crates/protocol/. Messages are serialized with postcard (a compact, no-std-compatible binary format) and length-prefixed for framing.

Control Messages (Bidirectional Stream)

pub enum ControlMessage { Handshake(Handshake), // Capabilities, codecs, display info ControlHandoff(ControlHandoff), // Grant/revoke remote control Goodbye { reason: String }, // Clean disconnect SetSharing { screen: bool, audio: bool }, // Toggle sharing } pub struct Handshake { version: u16, // PROTOCOL_VERSION = 1 capabilities: Vec<Capability>, // Screen, Audio, RemoteControl, etc. display_width: u16, // Host's display dimensions display_height: u16, display_scale: u16, // Retina scale factor video_codecs: Vec<VideoCodec>, // H264, H265, AV1 audio_codecs: Vec<AudioCodec>, // Opus }

Input Messages (Unidirectional Stream)

pub enum InputMessage { Key(KeyEvent), // key_code + modifiers (shift, ctrl, etc.) Click(MouseClick), // x, y, button, click_count Scroll(MouseScroll), // x, y, delta_x, delta_y Clipboard(ClipboardSync), // content (up to 1MB) }

Cursor Updates (Datagrams)

pub struct CursorUpdate { peer_id: u16, // Session-local peer ID x: u16, // Pixel position y: u16, visible: bool, // Is cursor on screen? click_animation: u8, // Ripple frame 0-10 } // Total: ~10-15 bytes — well under the ~1200 byte datagram MTU
Why postcard? postcard is a Rust-native binary serialization format. It's compact (no field names on the wire), fast (zero-copy deserialization), and no_std compatible. The tradeoff: it's NOT self-describing. Both sides must agree on the exact type layout. That's why the protocol crate versions message types.
Section 12

Where It's All Going

The networking stack is designed to grow. Here's how each layer evolves from 1:1 P2P to multi-party rooms and web viewers.

Multi-Party: Star Topology

Multi-Party Architecture (Planned)

Encode Once, Fan-Out

Host encodes video once. A broadcast::channel clones EncodedPacket to each guest's moq-lite publisher. Each guest drops old frames independently — a slow guest doesn't affect others.

Per-Guest Quality

Each connection has its own QualityMonitor. Guest A gets 1080p30 while Guest C gets 720p15. The encoder runs at the highest quality needed; downscaling happens per-connection.

Relay-Based Rooms

For 3+ participants, the host's upload bandwidth becomes the bottleneck. A moq-relay solves this — the host uploads once to the relay, and the relay fans out to all guests:

Host uploads 1 stream to relay. Relay sends N copies to N guests. Host upload stays constant regardless of guest count. The relay uses moq-lite's priority system to make forwarding decisions — it never decodes the media, just routes it.

Web Viewer

Because moq-lite is designed for WebTransport (QUIC in browsers) and hang frames are WebCodecs-compatible, a future browser client can subscribe to a pairwire broadcast natively:

The takeaway: Pairwire's networking stack is a layered system — UDP → QUIC → iroh → moq-lite → hang — where each layer solves one problem. QUIC gives us multiplexed, encrypted transport. iroh adds P2P connectivity. moq-lite adds media-aware pub/sub. hang adds codec semantics. And pairwire's transport crate glues it all together into a real-time pair programming session that works over any network, adapts to congestion, and scales from 1:1 to multi-party.
